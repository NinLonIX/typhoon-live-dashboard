# 沿海台风实况预警台：项目计划书

- **项目名称**：沿海台风实况预警台
- **文档版本**：V1.0
- **编写日期**：2026-09-26
- **目标用户**：沿海居民、沿海商户、渔民及家属、基层社区工作人员、短期出行人员
- **产品定位**：把权威台风实况、影响趋势和分级预警放在一个易读的移动优先页面中，帮助居民快速判断“现在发生什么、会往哪里走、我需要做什么”。

> 本计划书用于指导产品设计和第一版开发。网站属于公共风险信息展示工具，不能替代气象部门、海事部门、应急管理部门和地方政府发布的正式预警、避险命令或救援指令。

---

## 1. 项目背景与问题

台风信息通常分散在预警公告、路径图、新闻和多个天气应用中。沿海居民在手机上最需要的是一组明确答案：

1. **台风叫什么**：名称、编号、当前状态。
2. **台风在哪里**：中心经纬度、距离用户或重点城市多远。
3. **往哪里走**：移动方向、速度、未来路径和预计登陆区域。
4. **风力多大**：最大风力、最大风速、中心气压、影响等级。
5. **我该做什么**：当前预警等级对应的简短行动建议和权威通知入口。

项目要解决的是“信息找得到但判断很慢”，而不是制造一个新的预报来源。

---

## 2. 产品目标

### 2.1 第一阶段目标（MVP）

- 在首页首屏展示当前活跃台风的名称、编号、位置、方向、速度和风力。
- 使用地图展示历史路径、当前位置和未来路径；清楚区分“实况”和“预报”。
- 建立四级风险提示：蓝、黄、橙、红，并显示触发依据、发布时间、有效期和行动建议。
- 支持按城市/定位查看距离、预计影响时间和当地预警入口。
- 标出数据来源、数据时间、页面更新时间和数据延迟状态。
- 在弱网、手机小屏和无定位权限场景下仍能阅读核心信息。

### 2.2 暂不纳入 MVP

- 自行生成气象预报或修改官方预报结论。
- 代替政府发布紧急指令、疏散通知或救援调度。
- 复杂的用户社交、评论、直播和商业广告系统。
- 没有授权的数据抓取、付费数据转售或跨地区预警规则混用。

## 3. 信息架构与页面规划

### 3.1 首页：台风总览

首屏按以下顺序展示：

1. **风险横幅**：当前最高预警等级、更新时间、是否存在数据延迟。
2. **台风卡片**：名称/编号、强度等级、当前中心位置、移动方向与速度。
3. **风力指标**：最大风力、最大风速、中心气压、七级风圈/十级风圈（数据可用时）。
4. **路径地图**：历史轨迹、当前点、未来预测轨迹、预测时间点、影响海域和登陆标记。
5. **重点城市列表**：城市距离、预计影响时间、当地预警、风雨摘要。
6. **行动建议**：按预警等级给出普通居民可执行的短句。
7. **权威来源**：来源机构、原文链接、发布时间和最近同步时间。

### 3.2 台风详情页

- 台风完整路径和时间轴。
- 每个观测点的时间、经纬度、最大风力、风速和气压。
- 预报路径与实况路径对照。
- 历史公告列表和变更记录。
- 影响城市、沿海区域和海上作业提示。

### 3.3 城市/我的位置页

- 以城市为中心显示距离和方位。
- 展示预计受影响时间窗，而不是只显示一个模糊日期。
- 显示当地气象预警、停航/停课/疏散等权威通知入口（有来源才展示）。
- 提供“订阅变更”入口；第一版可先做浏览器通知预留，不强制实现短信。

### 3.4 数据与免责声明页

- 数据来源和授权说明。
- 更新频率、延迟定义、缺测处理规则。
- 预警颜色的地区适用范围和解释。
- 免责声明、隐私政策、定位权限说明。

## 4. 预警分级设计

### 4.1 展示层级

采用四级颜色作为**统一展示层**：

| 等级 | 颜色 | 页面含义 | 展示要求 |
|---|---|---|---|
| 蓝色 | `#2563EB` | 需要关注 | 显示影响范围、准备物资、关注后续更新 |
| 黄色 | `#EAB308` | 影响可能加大 | 减少不必要出行，检查门窗、车辆和排水 |
| 橙色 | `#F97316` | 风险较高 | 避免前往海边、码头和危险区域，遵守地方安排 |
| 红色 | `#DC2626` | 风险极高/需要立即行动 | 服从当地政府和应急部门指令，必要时立即避险 |

### 4.2 分级规则

- 颜色只是跨地区的阅读辅助；页面必须同时显示**发布机构、原始级别、发布时间和适用区域**。
- 不把不同地区的官方阈值直接拼成一个全国阈值。各地区若采用不同标准，应以原文为准并在卡片上标注地区。
- 当数据来源冲突时，优先展示主管部门最新有效公告，并在“数据说明”中标记冲突。
- 预警取消、升级、降级都作为事件记录保存，不能只覆盖当前状态。
- 若数据超过设定时限未更新，显示“数据可能延迟”，不继续暗示实时有效。

### 4.3 行动文案原则

- 每条建议不超过两行，使用动词开头，例如“远离海边”“检查门窗”“关注当地通知”。
- 不承诺“安全”“一定登陆”或“不会影响”。
- 红色等级必须把地方政府/应急部门的正式指令放在最显眼的位置。

## 5. 数据方案

### 5.1 首选来源

优先接入有公开授权和稳定更新机制的权威来源，例如国家或地方气象部门、海事部门、应急管理部门的公开产品。具体接口、授权方式、更新频率和商业使用限制在开发前单独核实并记录。

### 5.2 统一数据对象（建议）

```ts
interface TyphoonSnapshot {
  id: string;
  name: string;
  internationalName?: string;
  number?: string;
  status: 'active' | 'dissipated' | 'unknown';
  observedAt: string;
  sourceUpdatedAt: string;
  center: { latitude: number; longitude: number };
  movement: { directionText?: string; bearing?: number; speedKmh?: number };
  intensity: {
    maxWindLevel?: number;
    maxWindSpeedKmh?: number;
    centralPressureHpa?: number;
  };
  warning?: {
    level: 'blue' | 'yellow' | 'orange' | 'red' | 'none';
    issuer: string;
    issuedAt: string;
    expiresAt?: string;
    areaText: string;
    originalLevelText?: string;
    advice: string[];
  };
  track: Array<{
    kind: 'observed' | 'forecast';
    at: string;
    latitude: number;
    longitude: number;
    maxWindLevel?: number;
    maxWindSpeedKmh?: number;
  }>;
}
```

### 5.3 数据处理要求

- 后端统一单位、时间格式和字段名称，前端不直接拼接不同来源的原始字段。
- 保存 `sourceUpdatedAt`、抓取时间、来源 URL、HTTP 状态和校验结果，便于追溯。
- 对经纬度范围、时间倒序、风速异常、重复台风编号做校验。
- 来源不可用时保留最近一次有效数据，并明显显示“最后有效更新时间”。
- 缓存应设置短 TTL；预警升级、取消等事件需要更快刷新或主动失效缓存。
- 原始公告与标准化数据分开保存，便于审计和重新处理。

## 6. 技术路线

### 6.1 推荐架构

- **前端**：TypeScript + React + Vite；移动优先响应式布局。
- **地图**：Leaflet 或同类 Web 地图库；支持缩放、图例、轨迹分层和无障碍文本替代。
- **数据层**：轻量后端或 Serverless API 作为数据代理、缓存、校验和聚合层。
- **存储**：MVP 可使用 PostgreSQL/SQLite 保存标准化快照与公告；对象存储保存原始公告快照。
- **部署**：前端静态部署，API 使用受控服务；密钥只放服务器环境变量。
- **监控**：数据同步成功率、数据延迟、来源错误率、前端错误和地图加载失败率。

### 6.2 安全与可靠性

- 不在浏览器暴露来源 API 密钥。
- 对外部数据做 schema 校验、限流、超时、重试和熔断。
- 记录人工修正和发布操作；保留回滚能力。
- 关键文字内容支持人工复核后再发布。
- 做键盘访问、屏幕阅读器、色弱对比度、字号放大和低带宽测试。

---

## 7. 交互与视觉要求

- 首屏先给结论：当前等级、台风位置、移动方向、风力和更新时间。
- 实况用实线和实心点，预报用虚线和空心点；提供文字图例，不能只靠颜色。
- 风险等级同时用颜色、文字和图标表达，避免色盲用户无法判断。
- 地图下方提供列表化信息，避免地图加载失败时信息不可用。
- 所有时间显示时区；默认显示用户所在时区，并允许切换中国标准时间。
- 更新后保留“较上次变化”：方向、速度、强度和预警是否升级/降级。
- 关键数字字号足够大，适合户外手机快速查看。

## 8. 开发阶段与里程碑

### 阶段 0：数据与合规确认（1 周）

- 确认权威来源、授权条款、字段、频率和故障联系人。
- 定义预警展示规则、免责声明和数据保留周期。
- 产出：数据源清单、字段映射表、风险规则说明。

### 阶段 1：MVP 原型（1 周）

- 完成首页信息架构、移动端线框图和地图图例。
- 用静态样例数据验证四级预警、空状态、延迟状态和异常状态。
- 产出：可点击原型、视觉规范、可用性问题清单。

### 阶段 2：核心开发（2 周）

- 完成数据代理、标准化模型、缓存、首页、详情页和城市页。
- 接入历史路径、未来路径、预警卡片和来源信息。
- 产出：测试环境可用版本、接口文档、错误日志。

### 阶段 3：可靠性与无障碍（1 周）

- 完成异常数据、来源不可用、延迟、重复事件和回滚测试。
- 完成移动端、低带宽、键盘操作、屏幕阅读器和色弱对比度测试。
- 产出：测试报告、上线检查表、应急联系人表。

### 阶段 4：试运行与上线（1 周）

- 以历史台风数据或沙盒数据做回放演练。
- 观察同步延迟、地图性能、错误率和用户理解度。
- 通过上线评审后发布；上线首周安排人工巡检。

## 9. 验收标准

### 功能验收

- 页面能在 3 秒内展示最近一次有效的核心信息（具体目标按部署环境复测）。
- 用户无需打开地图即可看到名称、位置、方向、风力、预警等级和更新时间。
- 实况与预报路径可区分；路径点点击后能查看时间和强度。
- 预警升级、降级、取消和数据延迟状态均有明确视觉与文字反馈。
- 来源、发布时间、更新时间和原始公告入口可追溯。
- 无定位权限时仍可按城市搜索；无活跃台风时有清晰空状态。

### 质量验收

- 手机窄屏无横向滚动，关键按钮和文字可读。
- 颜色对比度和非颜色提示符合无障碍要求。
- 外部来源超时或返回异常数据时，页面不崩溃且显示可理解的降级状态。
- 重要数据字段有自动校验，错误事件可在日志中定位。
- 上线前完成数据授权确认和正式免责声明审核。

## 10. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 数据源延迟或中断 | 实况不新 | 显示最后有效时间、延迟状态和备用来源 |
| 不同地区预警标准不同 | 用户误解颜色 | 保留原始级别、发布机构和适用区域 |
| 预测路径被误读为确定路径 | 错误决策 | 明确“预测”、时间点和不确定性说明 |
| 高并发访问 | 页面或 API 变慢 | CDN、缓存、静态降级页和限流 |
| 地图服务不可用 | 位置关系难理解 | 同步提供文字列表和表格化路径 |
| 关键公告变更快 | 旧信息传播 | 保存版本、标记变更、快速刷新预警卡片 |
| 误把网站当成官方指令 | 安全风险 | 全站显著来源说明、原文链接和免责声明 |

## 11. 后续迭代方向

1. 订阅指定城市或台风的升级、降级、取消通知。
2. 支持多语言和面向游客的简明模式。
3. 增加降雨、风暴潮、海浪和港口/航班影响（必须分别标明来源）。
4. 提供历史台风回放，用于社区培训和应急演练。
5. 增加“数据变化摘要”，帮助用户快速看到过去 6 小时的变化。
6. 建立公开状态页，展示同步是否正常、最后成功时间和当前数据延迟。

## 13. 成功指标（试运行阶段）

- 首屏核心信息可见率 ≥ 99%。
- 数据同步任务成功率 ≥ 99%（按已确认的数据源统计）。
- 关键页面移动端加载错误率低于约定阈值。
- 用户测试中，至少 90% 的参与者能在 10 秒内回答“台风名称、当前位置、移动方向和当前预警等级”。
- 所有展示中的预警卡片都能追溯到来源机构和原始发布时间。
